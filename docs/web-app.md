# Web app v1

Status: agreed with the repository owner on 2026-10-29 in a design session. Sections are built in the order of section 10. The look is shown in the board mock-up (the "Look" screens): https://claude.ai/artifact/7N2n8s3gW14KMZiNbMPRr1

Words used here follow [CONTEXT.md](../CONTEXT.md). The API the web app talks to is described in [api.md](api.md).

## 1. What the first release covers

- Sign in, sign up and sign out.
- The project list, with "New project".
- The board view: columns, cards, adding a card, dragging cards, and the board's chats in the sidebar.
- New chats, the "Create a card for this chat?" prompt, and linking or unlinking a chat and a card.
- Chat messages: reading, sending, editing and deleting messages in a chat, with Markdown, card-number links and website links (section 3; agreed 2026-11-09).
- The card panel with every card feature the API has: title, description, priority, due date, estimate, assignees and owner, labels, subtasks, checklists, time entries and the timer, completing and reopening, deleting, the Activity tab, and the open card's related cards (outlined on the board, and listed in the panel when they are on other boards; [card-features.md](card-features.md) section 7).
- Project settings: members (add by email, change role, remove, leave), labels, project code, time zone and the relationship colours ([card-features.md](card-features.md) section 7; admins only, saved straight away). Every member can open it; for people who are not project admins it is read-only, except that they can add a label and leave the project (agreed 2026-10-31). Removing someone, leaving, deleting a label and changing the code ask "Are you sure?" first; role and time zone changes save straight away (agreed 2026-10-31). Renaming a project and changing its description come later, with a small API change.
- A server admin screen with the sign-up switch, and nothing else for now (no list of accounts; agreed 2026-10-31). Server admins reach it from the account menu.

Live updates are covered in section 6 (built in the live-updates pull request). Not in this release: file attachments and AI features. Screenshots in messages (pasting or dropping images) come with file attachments, roadmap step 3 (agreed 2026-11-09). Link previews (a preview card under a web address) are left until after the MVP (agreed 2026-11-09).

## 2. Screens and addresses

| Address | Screen |
|---|---|
| `/sign-in`, `/sign-up` | Signing in, and making an account. When sign-up is off, the sign-in page hides its "Create an account" link and `/sign-up` says "Sign-up is closed. Ask your server admin for an account." (agreed 2026-10-30) |
| `/projects` | Your projects. When empty, it offers "Create your first project" |
| `/WEB` | A project. It opens the last board you used in it, or offers "Create your first board" when it has none (agreed 2026-10-30). With no board remembered in this browser, or one that has gone, it lists the project's boards, with "New board" |
| `/WEB/boards/<board id>` | A board |
| `/WEB-12` | Opens card WEB-12 on its board, with the card panel open. Old card numbers and project codes keep working |
| `/WEB/settings` | Project settings |
| `/admin` | Server settings, for server admins. Anyone else sees "Page not found". No project may use the code `ADMIN`, because addresses ignore letter case (agreed 2026-10-31) |

- After signing in you land on the **last board you used**. The first time, you land on the project list.
- If your session has ended, you are sent to the sign-in page and brought back to the same place afterwards.

## 3. Layout of the board screen

- A sidebar on the left lists the project's boards and the board's chats: the general chat first, then the chats not linked to a card. A card's chat is opened from its card. (Agreed 2026-10-31 as a trial.)
- A chat with no card asks "Create a card for this chat?" in the chat panel. "Create a card" makes a card in the board's first column with the chat's title, and the card takes that chat as its own. "Link to a card" picks a card on the board, found by number or title. Only cards without a chat are offered, because a card has at most one chat. A linked chat can be unlinked from the panel, and both are kept. (Agreed 2026-10-31.)
- **The chat panel's messages** (agreed 2026-11-09). Under the chat's title and card, the panel shows the chat's messages and, at the bottom, the message box. Every project member can read and post in every chat of the project.
  - **The list** is a labelled list (named "Messages"), oldest at the top and newest at the bottom. With none it says "No messages yet". Each message shows the author's name, when it was sent and the text as formatted Markdown (bold, italic, code, lists, links). The time uses the same wording as the Activity tab ("just now", "5 minutes ago", and so on); the exact time shows on hover and is read out by screen readers.
  - **Grouping.** When the same person sends several messages within 5 minutes of their previous one, with nobody else's message in between, only the first shows the name and time. The exact time stays available for screen readers.
  - **Edited and deleted messages.** An edited message shows "(edited)", and no earlier texts are kept. A deleted message stays in place with its text crossed out and "Deleted by Jon, 5 minutes ago" under it, and everyone can still read it. It has no menu and cannot be edited or deleted again. A delete is final; a password pasted by mistake cannot be fully removed in the MVP.
  - **Card numbers.** A card number written in a message, such as WEB-12 (an old number works too), becomes a link when the card is in this project. Clicking it opens that card's panel and keeps the chat panel open. A number that does not exist, or a code from another project, stays plain text. Only the first 20 different card numbers in one message are looked up and linked; the rest stay plain text (agreed 2026-11-10).
  - **Markdown that cannot be drawn** (agreed 2026-11-10). Markdown the toolbar cannot make (tables, images, task lists, headings, raw HTML, anything the app does not know) shows as the plain text that was written, never as an empty message. That includes a deleted message, whose crossed-out text stays readable. Each message is also drawn inside its own safety net: if one message cannot be drawn at all, it shows its text as plain written text, and the rest of the chat and the board keep working.
  - **Nesting limit** (agreed 2026-11-10). A message may nest lists and quotes at most 10 levels deep. Lists and quotes are counted the way Markdown reads them: quote marks count with or without spaces, lists nested inside quotes count, and every list mark on a line counts as its own level, code blocks (fences read as CommonMark does, also inside quotes and list items) and divider lines do not, and when it is unclear the message is refused. The message box refuses more with "Use at most 10 levels of lists and quotes" (the current wording; the owner has not objected), and the API gives 400.
  - **Typed text is never treated as HTML** (agreed 2026-11-10). In messages and in the card description, anything typed shows exactly as typed, wherever it is shown: the message, the read-only description, both editors and the Activity tab's "Show changes" view. For example `use <div> here`, `if a<b and c>d`, `<script>alert(1)</script> hi` and a literal `&lt;div&gt;` all stay as written, through saving, reopening the editor and saving again. The stored text keeps `<`, `>` and `&` as typed, apart from the escapes Markdown needs to read the text back as typed. The text is escaped as it is written: a line start that Markdown would turn into formatting (`#`, `>`, `-`, `+`, `1.`, `1)`) and an `&` that looks like an entity get a backslash or an extra escape (a typed `&lt;` is stored as `&amp;lt;`), plain `<`, `>` and `&` stay as typed, and code is never touched. Web addresses and email addresses are never escaped, `<https://…>` reads back with the right address, and table-like separator lines and lines with 4 or more leading spaces are kept as typed. This holds for the app's own Markdown reader, which reads HTML as plain text (it is not a global setting of the Markdown library), so it applies to the description too. **Typing shortcuts stay**: typing "1. " (or "10. ") at the start of a line in the message box starts a numbered list, as in the description. Text no shortcut matches, such as "1) one", stays as typed.
  - **Editing never crashes the chat** (agreed 2026-11-10). If the edit box cannot open a message's body, or the body holds anything it cannot hold (headings, quotes, code blocks, dividers, tables, images, task lists, footnotes), the person edits it as plain text, in a plain box labelled "Message" with Save and Cancel. The rest of the chat and board keep working.
  - **Former member** (agreed 2026-11-10). A message whose author's account was deleted shows "Former member" as the name, and "Deleted by Former member" when the deleter's account was deleted. The card Activity tab uses the same words.
  - **Website links.** A web address typed or pasted as `https://…` or `www.…` turns into a link by itself, and the toolbar's Link button puts a link on selected words. Links open in a new browser tab with `rel="noopener noreferrer"`. Only http, https and mailto links are made into links, so a `javascript:` link shows as plain text.
  - **The message box** (labelled "Message") is a small Tiptap editor, like the description, with a toolbar: Bold, Italic, Code, Link, Bulleted list and Numbered list, and a Send button. The text is stored as Markdown. **Enter sends** and **Shift+Enter starts a new line**. Blank text sends nothing. Text over 10,000 characters is refused with "Use at most 10000 characters", using the shared rules, so the box gives the same answer as the API.
  - **Sending.** A sent message shows straight away, faded and marked "Sending…" for screen readers, until it is saved. If saving fails, it stays in the list with "Couldn’t send" and a "Try again" button that sends it again. Each new message gets an id from the browser and "Try again" reuses it, so a message is never posted twice (agreed 2026-11-10). When the server refuses the message (a 4xx answer), its own words show instead of "Couldn’t send".
  - **Drafts.** Text you have typed but not sent is kept for each chat while the page is open. Switching to another chat and back shows it again, and it clears once sent. It is not kept if the page is reloaded.
  - **Editing and deleting.** Your own messages that are not deleted have a "Message options" menu with Edit and Delete. A project admin's menu on someone else's message has only Delete; a plain member sees no menu on others' messages. Edit replaces the message with an editor holding its text, with Save and Cancel. Enter saves and Escape cancels, as the buttons do (small choices made while building, covered by tests). The length and blank rules apply, and when the edit is over, keyboard focus goes back to "Message options". Delete asks "Delete this message?" with Delete and Cancel; Cancel sends nothing and focus returns to the menu button. A failed edit shows the server's message for a 4xx answer, or "Couldn’t save, try again", and keeps the message as it was. A failed delete closes the dialog and shows the error on the message.
  - **Loading and scrolling.** A chat opens at the bottom with its latest 50 messages. Scrolling to the top loads the 50 before them and keeps your reading position; a "Show older messages" button at the top does the same for keyboard users, and goes away when there are no older messages. The loaded list only grows: when a reload finds new messages while older pages are loaded, every message already shown stays shown until the chat is closed (agreed 2026-11-10). Older messages kept on screen stay current too: when someone else edits or deletes one, it is refreshed in place (section 6). If you have scrolled up and new messages arrive, the list does not jump: a "New messages ↓" button appears, which scrolls to the bottom and then goes away. When you are at the bottom, new messages scroll into view. If the messages cannot be loaded, the panel says "Couldn’t load the messages" with "Try again".
  - **Reloading.** The messages reload when another person sends, edits or deletes one (live updates, section 6), when you come back to the browser tab, and after your own changes. There is no reload on a timer.
  - **Left out of the MVP** (agreed 2026-11-09): unread markers, @mentions (they belong with notifications) and lines in a card's Activity tab for messages in its chat.
- The board's columns fill the middle.
- While a timer runs, a **timer chip** sits in the top bar of every signed-in screen. It shows the number of the card the timer runs on (a link to that card), the running time, and a "Stop timer" button (agreed 2026-11-07). Stopping from the chip when the timer ran under half a minute shows "Under half a minute, nothing saved" in the top bar for 6 seconds. If stopping fails, the chip says "Couldn't stop, try again" (agreed 2026-11-08).
- The **card panel** and the **chat panel** are two separate panels, so you can read a card's chat while editing the card.
- When threads arrive (after the MVP, see [roadmap.md](roadmap.md)), a message's **thread** (its replies) opens in its own sub-window, not inline in the chat (agreed 2026-10-31).
- People can dock the chat panel on the right, left or bottom, and drag its edge to resize it. A floating window and a separate browser window may come later, so the panel code must not assume where it sits.
- Clicking a card opens only its **card panel**, on the right of the board, with an edge that can be dragged to resize it. The panel has an "Open chat" button for the card's chat (agreed 2026-11-01). The address then ends in `?card=<id>`, so Back closes the panel.
- The card panel has two tabs, **Details** and **Activity** (agreed 2026-11-03). Details is shown when a card opens and holds everything else in this section. Switching to Activity and back keeps unsaved text, and "Discard your changes?" still asks when you leave the card. The **Activity** tab lists what was done to the card, newest first, one line each: the person's name, what they did, and when, for example "Jon moved this from To do to In progress, 3 hours ago". The sentence for each kind of change is in [card-features.md](card-features.md) section 9 (agreed 2026-11-08). The line has no edit or delete controls. It loads when the tab is opened and again after a change is saved in the panel. It shows 50 lines, with "Show older" for more while there are older ones. With nothing yet it says "No activity yet". If loading fails it says "Couldn't load the activity" with "Try again", and a failed "Show older" shows the same message above the lines, keeps the lines already shown, and leaves "Show older" in place to try again. While lines load, the tab says "Loading…". If a save finishes while older lines are loading, the older lines are kept (agreed 2026-11-08). "Show older" is turned off while the history reloads after a save, as well as while older lines load, and works again once the reload finishes (agreed 2026-11-08). Older lines load only when "Show older" (including pressing it again after a failure) is pressed: a save reloads only the pages already shown, never loads an extra older page, and never retries a failed older page by itself (agreed 2026-11-08). The time of each line reads "just now" under a minute, then "5 minutes ago", "3 hours ago", "2 days ago", "4 months ago" or "1 year ago". These update every minute while the Activity tab is open (agreed 2026-11-08). A line of a kind this page does not know yet reads "<name> made a change this page can’t show yet", and the page does not crash (agreed 2026-11-08). A change to the description has a "Show changes" button that opens, in place, the old and new text side by side, labelled "Before" and "After", exactly as saved, with "(empty)" when there was none (agreed 2026-11-08).
- The card panel is one self-contained component. The board screen only decides where it is placed, so it can move into a dialog or onto its own page later with a small change.
- Panel positions are remembered in the browser for now. They must move to the person's account later (this needs a small API addition).
- Desktop and tablet come first. On a phone the screen stays usable: panels stack, and the card and chat panels become tabs.

## 4. Cards on the board

- Cards can be dragged up and down within a column and into other columns. Dragging also works with the keyboard, and every card has a "Move to" menu as a non-drag option.
- Dropping a card into a done column while some of its subtasks are open asks "Complete anyway?" first.
- A card shows its number, title, priority (when set), labels, due date, checklist and subtask progress, and its assignees. Checklist progress on the board is one total across all the card's checklists ("3 of 7"); the card panel shows each checklist's own progress (agreed 2026-10-30).
- The API's "move card" takes a `position` in the column, which covers both reordering within a column and dropping into another column at a chosen place (agreed 2026-10-29). Reordering within a column is not recorded in the card's history.

## 5. Editing

- The description is edited with a formatting toolbar (Tiptap) and stored as Markdown, as [card-features.md](card-features.md) says. It has Save and Cancel buttons.
- Small fields (title, priority, due date, estimate) save as soon as they change. Due times are typed in the project's time zone, which is shown next to the box (agreed 2026-11-01).
- Leaving a card with unsaved changes to its description asks "Discard your changes?" first.
- Everyone can see the "Delete card" button. For people who may not delete the card (only its creator or a project admin may), it is turned off and says why (agreed 2026-11-01).
- **Checklists** sit under the description. Each shows its name and its own progress ("2 of 4"), then its items as tick boxes (agreed 2026-11-03):
  - "Add checklist" asks for a checklist name. "Add item" adds an item at the bottom: Enter adds it and leaves the "New item" box open for the next one. Clicking an item's text edits it: Enter saves, Escape puts it back, and clicking away saves it. Renaming a checklist works the same way.
  - Items are reordered within their checklist by dragging (with the keyboard too: Space, the arrow keys, Space), or with "Move up" and "Move down" in the item's menu. The item's menu also has Delete and "Turn into subtask" ([card-features.md](card-features.md) section 2). "Turn into subtask" is turned off on a card 5 levels deep, and says "Subtasks can only go 5 levels deep".
  - Each checklist's menu has Rename, Move up, Move down and Delete. Delete asks "Delete 'Testing' and its 6 items?" first.
  - The limits come from the shared rules, so the form and the API give the same answer: a name up to 100 characters, an item up to 500, and a name or item that is empty or only spaces is refused with "This can’t be empty" (the same words as the app's other forms). One that is too long is refused with "Use at most 100 characters" (or 500 for an item). At 100 items "Add item" is turned off and says "A checklist holds up to 100 items". If the "New item" box is open when the list fills, it closes, any half-typed text is cleared, and the keyboard focus moves to that reason only if you were typing in that box. If you were somewhere else (for example editing another item), focus stays where it is, so that edit is not saved early.
  - Adding an 11th or later checklist shows a note: "This card has a lot of checklists. Would a new card be clearer?" Its "Create a card" button opens the board's Add card form in this card's column. The checklist is still added.
- **Subtasks** sit under the description, with the checklists (agreed 2026-11-04; row and form layout approved from a mock-up on 2026-11-07):
  - The section heading shows "N of M complete" (direct subtasks only, as [card-features.md](card-features.md) section 4 says). With none, it says "No subtasks yet".
  - Each row has a tick box, the subtask's number and title as a link (it opens in the panel, or on its own board when it is on another one), its column and board, and its own subtask progress ("1 of 2") when it has subtasks. An "Options for WEB-12.1" menu has "Move to another parent" and "Make its own card".
  - Ticking a subtask that has open subtasks asks "Complete anyway?" first. After a tick, the row offers "Completed. Move it to Done?" with "Move" and "Keep here" ([card-features.md](card-features.md) section 5).
  - "Add subtask" asks for a title and a column. The column list is grouped by board, and starts on the parent's column. Any column of any board in the project can be picked. On a card 5 levels deep "Add subtask" is turned off and says "Subtasks can only go 5 levels deep".
  - "Move to another parent" opens a picker, also named "Move to another parent". It finds a card by its number or by words from its title, in the same project. It leaves out the subtask's current parent, the subtask itself and every card under it (agreed 2026-11-07). Results that are too deep to take the subtask (the moved card's own subtasks would pass 5 levels) are shown turned off and say "Subtasks can only go 5 levels deep" (agreed 2026-11-07). When the picker closes, keyboard focus goes back to whatever opened it (agreed 2026-11-07). When the person's own "Move to another parent" or "Make its own card" on a subtask row succeeds, that row is gone, so focus goes to the Subtasks heading. This holds even if a reload removed the row while the change was still saving: once the change succeeds, focus goes to the heading only if focus is on nothing (the page). If the person has put focus somewhere else, it stays there. If the change fails, focus is not moved. If a picked move fails after its picker has closed (a reload removed the row, or the picker was closed while the move was saving, from a row or from "Card options"), the failure shows in the card panel's message area, like a failed "Make its own card"; while the picker is open, the picker shows it. If the picker is cancelled, or the row disappears for any other reason (someone else's change, a reload while none of the person's own changes is saving), focus stays where it is (agreed 2026-11-07; the two rules about a reload during saving agreed 2026-11-07).
  - A subtask shows a line under the card's title: "Subtask of WEB-12 Build sign-in", linking to its parent. A top-level card has no such line. A subtask's direct parent is shown only in this line, not again under "Related cards on other boards"; grandparents and higher levels on other boards are still listed there (agreed 2026-11-07).
  - A subtask's panel header has a "Card options" menu (next to the close button) with "Move to another parent" and "Make its own card". "Delete card" stays a plain button.
  - In the Delete card dialog, a subtask's third choice is "Move to another parent". Choosing it opens the picker straight away, and the dialog says "Moves under WEB-15" once a parent is picked. Delete stays turned off until every subtask marked to move has a parent. The picker here leaves out the card being deleted and every card under it, because none of them will be left to be a parent. If the Delete card dialog is cancelled, focus goes back to the "Delete card" button. After the card is deleted, the panel closes and focus goes to the heading of the column the card was in (agreed 2026-11-07).
- **Time** sits in the card panel, with the checklists and subtasks. Its heading is "Time" (agreed 2026-11-08):
  - The top line reads "Estimate 2h · Time spent 1h 15m · Left 45m". When the time spent is over the estimate, "Over by 15m" replaces "Left". A card with subtasks also shows a second line: "Original estimate 2h" (its own estimate) and "of which 45m on this card" (agreed 2026-11-07). The estimate and "Time spent" are the rolled-up totals ([card-features.md](card-features.md) section 6).
  - "Start timer" starts the timer on this card. While it runs here, the button reads "Stop timer" and the running time shows next to it. If a timer is already running on another card, "Start timer" asks "Stop the running timer?" with "Stop it and start here" and "Cancel". Stopping that timer saves its time (button names agreed 2026-11-07, dialog title 2026-11-08). Stopping a timer in the panel that ran under half a minute shows "Under half a minute, nothing saved" beside the button (agreed 2026-11-08).
  - The **Entries** list (heading "Entries") shows everyone's time, newest day first. Each row has the person, the day ("2 Nov", with the year when it is not the current year in the project's time zone, agreed 2026-11-08), the time ("1h 15m"), the note, and a "Timer" tag when the timer made it. With no entries it says "No time logged yet". If the project's members cannot be loaded, the error shows in the Entries section (agreed 2026-11-08).
  - "Log time" opens a form with Hours, Minutes, Date and Note, and Save and Cancel. Date starts on today in the project's time zone, later days cannot be picked, and "Days are in Europe/London" (the zone) is shown under it. Edit uses the same form. Save is turned off while saving. Edit sends only the fields the person changed, compared with the values the form opened with. If the entry was changed elsewhere meanwhile, the person's change is saved and the other change stays. An Edit that changes nothing just closes (agreed 2026-11-08). The form checks the shared rules first. Errors: "Choose a day", "Use whole numbers", "Minutes go up to 59", "Log at least 1 minute", "Log at most 24 hours at a time" and "Use at most 1000 characters" (agreed 2026-11-08).
  - Each row has plain "Edit" and "Delete" buttons (not a menu). A person who may not use them sees them turned off, with the reason as text under the row: "Only a project admin can change someone else’s time", or "You can change your own time for 24 hours. After that, ask a project admin" (agreed 2026-11-03). Delete asks "Delete this time entry?" with "Are you sure?" and what will be deleted. After an entry is deleted, focus goes to the "Entries" heading (agreed 2026-11-08).
  - An entry from a timer left running past 24 hours shows "Needs review" and a "Confirm" button, which follows the same rules as Edit (agreed 2026-11-07). Confirm is turned off while saving (agreed 2026-11-08).
  - When "Delete card" is refused because the card has time logged, a project admin sees a "See the time entries" link in the dialog. It closes the dialog and moves focus to the "Entries" heading (agreed 2026-11-07).
- Quick actions such as dragging a card or ticking a checklist item show on screen straight away. If saving fails, the change is undone and a short message says why. When the server refuses the change (a 4xx answer, for example "Card not found"), the message is the server's own words. For network problems and server errors it says "Couldn't save, try again". If the server's message starts with a field name and a colon (for example "title: "), that prefix is dropped, so the person sees only the message. Before saving, the card panel checks the shared length limits itself, the description included (up to 50,000 characters; longer is refused with "Use at most 50000 characters"), so the form and the API give the same answer (agreed 2026-11-07). A refusal or failure message shows above the tabs of the card panel, so it is visible from both Details and Activity (agreed 2026-11-08).

## 6. Keeping screens up to date

Built in the live-updates pull request (plan agreed 2026-11-13). The API sends small "something changed" **signals** over a live connection, and the app reloads just what a signal names through the normal API. Nothing private travels over the connection. How it connects, and the signal shapes, are in [api.md](api.md) ("Live updates"); why it works this way is in [ADR 0002](adr/0002-live-updates-signals-then-reload.md).

- **What updates live** (when someone else makes the change):
  - the board: cards moved, added, edited or deleted;
  - the open card panel, with its checklists, subtasks, assignees, labels, time, chat link and Activity;
  - the sidebar's chat list;
  - the open chat's messages: new, edited and deleted ones, including older messages kept on screen. A new message while you have scrolled up shows the "New messages ↓" button, as in section 3.
- **What does not update live:** project settings, members, labels and the project list. A screen reloads them when you come back to the browser tab. Reloading on coming back to the tab stays for everything, as a safety net.
- **No reload on a timer.** The earlier 30-second reload is gone.
- **One connection per signed-in tab.** It joins the open board's room, and joins the new one when you change board. Signing out closes it. Every save the app sends says which connection made it (`X-Live-Connection`), so a tab ignores the signals about its own changes, which are already on screen. A signal that arrives while your own save of the same thing is still in flight never undoes that save.
- **"Reconnecting…" bar.** If the connection has been down for more than 3 seconds, a bar with "Reconnecting…" shows at the top of the app (a polite status message for screen readers). Down for 3 seconds or less shows nothing. When the connection is back, the bar goes away with no "Back online" message, the board room is joined again, and the board, the open card, the chat list and the open chat reload once to catch up.
- **Someone removed from the project** while looking at a board gets no more live changes. The next reload (for example coming back to the tab) shows the usual "not found" screen.
- **Two people changing the same field: the last save wins.** Your edit is never overwritten while you are typing. Instead:
  - **Only the same field counts.** A change to a part of the card you are not editing just appears and leaves your box alone: for example a new checklist while you edit the description, checklist item B while you edit item A, or the title while you edit the description.
  - **Same field changed.** The fields that can show a conflict are the card title, the description, a checklist item's text, a subtask's title (the title of a subtask card opened in the card panel) and your own message while you edit it. Your text stays in the box. Under it a panel says "Someone changed this while you were editing." (no name) and shows their new version, formatted as it is read for the description and messages.
  - **Use theirs** replaces your text with theirs; the field stays open for editing and the panel closes. **Keep mine** closes the panel and keeps your text. **Save** at any time saves your text over theirs. **Cancel** closes the field and shows their version; on the description it still asks "Discard your changes?" while the panel shows. If they change it again while the panel is open, it shows the newest version. The buttons work by keyboard.
  - While the panel shows, clicking away does not save the title or a checklist item. Only Save, Enter, Use theirs or Keep mine act.
  - **Pickers** (assignees, labels, dates, priority and similar) save the moment you pick, so another person's change just shows.
  - **Your message deleted while you edit it:** the editor closes and the message shows crossed out with "Deleted by …". Nothing is sent.

## 7. Look

- Tailwind CSS for styling, and Radix for accessible building blocks (menus, dialogs, tabs).
- The mock-up's colours and the Inter font.
- Accessibility target: WCAG 2.2 AA (keyboard use, screen readers, contrast), with automatic checks (axe) in the tests.

## 8. Code structure

- The API's input rules (zod schemas) move into a shared package, `packages/shared`, used by both apps. Forms then show the same errors the API would give.
- The web app and the API are served from the same address, so the sign-in cookie just works. During development the web app's dev server passes `/api` requests, and the live connection (`/socket.io`, WebSocket upgrades included), on to the API. In production the API also serves the built web app, so `npm run start:prod -w apps/api` runs everything on one address (agreed 2026-10-30). See [ADR 0001](adr/0001-web-app-and-api-on-one-origin.md).
- What the API sends back is described by plain TypeScript types in `packages/shared` (`responses.ts`). The answers are not checked again at run time, because both apps are built together (agreed 2026-10-30).
- Data loading uses TanStack Query (caching, reloading on tab focus and when a live signal names it, undoing a failed change). The live connection uses `socket.io-client`. Addresses use React Router. Dragging uses dnd-kit. (Library choices are confirmed in each PR's plan.)
- **Markdown libraries** (agreed 2026-11-10, chat messages): `marked` is a direct dependency of the web app, and the app reads Markdown with its own reader that treats HTML as plain text, instead of changing the library's global settings. `@tiptap/markdown` is pinned to an exact version (no automatic upgrades), because the as-typed escaping of messages and descriptions relies on its internals; upgrade it on purpose, with the tests.

## 9. Testing

- Component tests with Vitest and Testing Library, describing what a person sees. The API is faked with MSW.
- A few end-to-end tests in a real browser (Playwright) against the real API in CI: sign in, create a card, move it, open it. They run in their own CI job ("Browser"), which starts PostgreSQL and the API serving the built web app (agreed 2026-10-30). They also check accessibility with axe, colour contrast included.
